# 过度设计审查报告

## 审查依据

本报告依据仓库根目录的 `AGENTS.md` 编写，重点检查以下问题：

- 是否为了单一功能引入了超出当前需求的复杂度
- 是否新增了多套真值来源或过多抽象层
- 是否把 AI 辅助能力扩展成了难以维护的规则系统
- 是否复用了现有表单与流程，而不是重建并行体系

审查范围：

- `backend/server.py`
- `frontend/index.html`
- `frontend/static/js/app.js`
- `frontend/styles.css`
- `tests/test_api_smoke.py`

## 结论

当前实现**已经完成**，而且主链路是成立的：一句话输入 -> 生成草稿 -> 回填现有表单 -> 用户确认创建。

从“是否过度设计”的角度看，结论是：

- 整体没有失控
- 前端方案基本克制
- 后端存在**轻到中度过度设计倾向**
- 主要问题集中在 `backend/server.py` 中为本地兜底写入了较大体量的规则解析逻辑

换句话说，这次实现没有走到“架构灾难”，但已经出现一个明确的复杂度热点，后续如果继续在同一方向堆规则，维护成本会明显上升。

## 主要发现

### 1. 后端本地解析器体量偏大，已接近单功能微型规则引擎

位置：

- `backend/server.py:404`
- `backend/server.py:422`
- `backend/server.py:472`
- `backend/server.py:502`
- `backend/server.py:551`
- `backend/server.py:577`
- `backend/server.py:666`
- `backend/server.py:696`
- `backend/server.py:719`
- `backend/server.py:743`
- `backend/server.py:756`
- `backend/server.py:819`
- `backend/server.py:855`
- `backend/server.py:911`

判断：

- 为了实现“AI 草稿失败时可回退”，当前在一个文件里补入了日期解析、时间解析、人名提取、关键成员提取、活动名提取、提示语提取、默认值合并、JSON 提取、AI 提示词构造等整段逻辑。
- 这让 `server.py` 从“Flask 接口 + 核心业务”进一步膨胀成了“接口层 + 规则解析层 + AI 协调层”的混合文件。
- 按 `AGENTS.md` 的标准，这已经触发了“单个文件因一个功能增长出大段解析、协调、兜底逻辑”的过度设计信号。

为什么现在还没到严重：

- 这些逻辑仍然服务于一个明确需求，没有继续抽出多层抽象框架。
- 当前没有额外引入 parser class / DSL / pipeline engine / service container，这一点是克制的。
- 失败路径和人工确认路径都还清楚。

结论：

- 这是本次实现里最明显的复杂度热点。
- 现在可以接受，但不适合继续沿同一文件继续堆更多自然语言规则。

### 2. 前端没有重建第二套创建流，这一点是合理设计，不算过度

位置：

- `frontend/index.html:130`
- `frontend/static/js/app.js:144`
- `frontend/static/js/app.js:171`
- `frontend/static/js/app.js:225`
- `frontend/static/js/app.js:416`
- `frontend/static/js/app.js:476`

判断：

- 新功能没有做成独立“AI 建表页”或单独提交流，而是复用了原有创建表单。
- `generateCreateDraft()` 只是请求草稿并调用 `applyCreateDraftToForm()` 回填，最终仍然走 `createSession()`。
- 这符合 `AGENTS.md` 里“优先把新能力接入现有表单和现有提交流程”的要求。

结论：

- 这是合理复杂度，不属于过度设计。

### 3. `requiredNames` 与 `participants[].isRequired` 是双源数据，但当前属于业务必要，不算明显过度

位置：

- `backend/server.py:278`
- `backend/server.py:327`
- `backend/server.py:381`
- `backend/server.py:1024`
- `backend/server.py:1453`
- `backend/server.py:1549`
- `backend/server.py:1572`

判断：

- 现在同时存在“会话级关键成员预设”与“参与者已加入后的关键成员状态”两套表达。
- 这确实带来了同步成本，因此从设计角度看是一个风险点。
- 但该双源并非纯粹为了未来扩展，而是为了解决“人还没加入时，也要先把关键成员意图保存下来”这个当前真实需求。

结论：

- 这是有代价但合理的业务复杂度。
- 暂不认定为过度设计，但后续需要严格控制同步逻辑，不要再衍生第三套来源。

### 4. 测试覆盖是克制的，做法正确

位置：

- `tests/test_api_smoke.py:380`
- `tests/test_api_smoke.py:408`

判断：

- 当前只补了两个关键测试：草稿接口结构化输出、关键成员预设在加入时自动继承。
- 这属于“补主链路测试”，没有演变成超大规模测试矩阵。

结论：

- 这部分不是过度设计，反而是合理收口。

## 综合评级

评级：**轻到中度过度设计倾向，集中在后端本地解析兜底**

具体判断：

- 产品路径：克制
- 前端接入：克制
- 测试策略：克制
- 后端自然语言兜底：偏重

## 建议

### 现在不要做的事

- 不要继续往 `backend/server.py` 里追加更多日期口语、时间语法、人名规则。
- 不要把本地解析再扩成完整自然语言引擎。
- 不要为这个功能再引入额外的状态层或配置层。

### 下一步更合适的收口方式

- 如果后续继续增强自然语言建表，优先把草稿解析逻辑迁到独立模块，例如 `backend/create_draft.py`，先做物理拆分，不做过度抽象。
- 保持“AI 输出草稿 + 人工确认”的产品边界，不要追求 AI 直接建表。
- 如果线上 AI 可用率足够高，可以考虑逐步缩减本地规则，只保留最基础的 fallback，而不是继续把 fallback 做重。

## 最终结论

代码里**确实存在过度设计迹象**，但范围可控，主要集中在后端本地规则解析部分。  
如果你现在问我“这版该不该推翻重做”，答案是否定的。  
如果你问我“下一步最该警惕什么”，答案是：**不要再在 `backend/server.py` 里继续堆规则。**
