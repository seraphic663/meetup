# 【meetup：项目审查】

## 审查目标

本报告清空上一轮“功能兜底过度”的结论，重新审查当前代码里仍然存在的“丑陋、冗长、不必要、难维护”的实现。

本次不再讨论已经处理过的 AI 本地 NLP 兜底和旧表格开放删除兼容；重点转向代码形态本身：文件是否过长、职责是否混杂、重复是否明显、前后端是否把结构/样式/行为揉在一起。

## 总结论

当前项目主链路可用，测试覆盖也能兜住核心接口。但代码层面仍有明显“堆出来”的痕迹，主要集中在前端：

- `frontend/static/js/app.js` 已经变成前端总控大文件，职责过多。
- `frontend/static/js/render.js` 用大量字符串模板生成复杂表格，重复、脆弱、难局部修改。
- `frontend/index.html` 仍有大量 `onclick` 和内联 `style`，结构、行为、样式混杂。
- `backend/server.py` 仍然承担路由、校验、鉴权、归一化、总结、AI 协调等多类职责，虽然还能维护，但已经偏厚。
- `tests/test_api_smoke.py` 是一个大型冒烟测试文件，覆盖有效，但越来越像“全功能回归脚本”，后续定位失败会变慢。

评级：**中度代码过度，前端重于后端。**

最该先清理的是：`app.js` 和 `render.js`。  
最不该马上做的是：把后端拆成复杂 service/repository 架构。

## 主要问题

### 1. `frontend/static/js/app.js` 是当前最明显的大杂烩

位置：

- `frontend/static/js/app.js:23`
- `frontend/static/js/app.js:350`
- `frontend/static/js/app.js:412`
- `frontend/static/js/app.js:553`
- `frontend/static/js/app.js:728`
- `frontend/static/js/app.js:856`
- `frontend/static/js/app.js:922`
- `frontend/static/js/app.js:1013`
- `frontend/static/js/app.js:1131`

现状：

- 文件超过 1100 行。
- 同时负责：设置偏好、创建表格、AI 起草、加入会话、填写保存、拖拽交互、轮询、教程、分享、复制链接、管理弹窗、删除/退出、启动初始化、全局函数挂载。
- 文件尾部通过 `Object.assign(window, {...})` 暴露大量函数给 HTML 的内联 `onclick` 调用。

为什么丑：

- 它不是一个“入口文件”，而是入口、控制器、交互层、页面动作集合、弹窗管理器混在一起。
- 任意小交互都容易继续往这里追加函数。
- 删除/退出这类动作已经出现 current 和 history 两套函数：`deleteCurrentSession()` / `deleteSessionFromHistory()`，`leaveCurrentSession()` / `leaveSessionFromHistory()`。
- 管理弹窗相关函数从 `renderManageParticipants()` 到 `saveManagedSession()` 形成一个小模块，但仍塞在 app.js 中。

建议优先处理：

- 先做物理拆分，不做框架化重构。
- 可拆出：
  - `frontend/static/js/session-actions.js`：创建、加入、删除、退出、保存填写。
  - `frontend/static/js/manage.js`：管理弹窗和参与者编辑。
  - `frontend/static/js/drag.js`：格子拖拽填写。
  - `frontend/static/js/share.js`：分享和复制链接。
- `app.js` 保留初始化、页面切换和模块协调。

收益：

- 以后改某个弹窗或动作时不用穿过 1000 行入口文件。
- 测试和手测路径更容易定位。
- 降低继续把新功能都塞进 `app.js` 的惯性。

### 2. `frontend/static/js/render.js` 的表格渲染重复且脆弱

位置：

- `frontend/static/js/render.js:187`
- `frontend/static/js/render.js:253`
- `frontend/static/js/render.js:342`

现状：

- `renderDayByTime()` 和 `renderDayByParticipant()` 都在手写大量 table 字符串。
- 两套布局都重复处理：当前用户、其他用户、折叠列、不可填写区、关键成员标记、状态格子、汇总格子。
- 大量状态直接通过字符串拼接成 HTML、class、style、data 属性和 inline handler。

为什么丑：

- 两种布局的共同概念没有被提取，例如 participant cell、blocked cell、toggle row、required marker。
- 修改关键成员显示、不可填写区样式、折叠行为时，容易漏改另一套布局。
- 行内 `style="display:none"` 和 `style="background:..."` 让渲染层同时承担布局状态和视觉状态。

建议优先处理：

- 不要马上换框架，也不要引入虚拟 DOM。
- 先抽小函数：
  - `renderParticipantName(participant, isMe)`
  - `renderBlockedCell(kind, hidden)`
  - `renderStatusCell(...)`
  - `renderToggleRow(colspan)`
  - `hiddenAttr(isHidden)`
- 把颜色样式尽量变成 CSS 变量或 class，减少 inline style。

收益：

- 表格仍然可以字符串渲染，但不再是一整坨模板。
- 后续新增筛选/聚焦视图时，不会再复制一套大表格模板。

### 3. `frontend/index.html` 仍混杂结构、行为和样式

位置：

- `frontend/index.html:31`
- `frontend/index.html:41`
- `frontend/index.html:112`
- `frontend/index.html:121`
- `frontend/index.html:123`
- `frontend/index.html:124`
- `frontend/index.html:173`
- `frontend/index.html:256`
- `frontend/index.html:350`
- `frontend/index.html:377`

现状：

- 大量按钮直接写 `onclick="..."`。
- 多处保留内联 `style`，例如 hero 指标、创建页 AI 输入区、按钮样式、弹层背景点击等。
- HTML 既描述结构，又绑定行为，又夹杂视觉细节。

为什么丑：

- 这迫使 `app.js` 把函数挂到 `window` 上。
- 新增行为时容易继续复制 `onclick` 模式。
- 样式难以统一收口，尤其已经有完整 `styles.css` 的情况下，内联样式显得很突兀。

建议优先处理：

- 先清内联样式，全部迁回 `styles.css`。
- 再逐步把 `onclick` 改为 JS 里集中绑定。
- 不要求一次性改完整站，可以从创建页和管理弹窗开始。

收益：

- HTML 回到结构层。
- `window` 全局暴露函数可以逐步减少。
- 样式修改更集中。

### 4. `backend/server.py` 仍然偏厚，但暂不建议大拆

位置：

- `backend/server.py:206`
- `backend/server.py:255`
- `backend/server.py:300`
- `backend/server.py:353`
- `backend/server.py:556`
- `backend/server.py:628`
- `backend/server.py:804`
- `backend/server.py:980`

现状：

- 文件超过 1100 行。
- 同时包含：请求处理、输入校验、session 归一化、参与者归一化、鉴权、可用性裁剪、总结排序、AI prompt、路由。
- `create_draft.py` 中也有 `_clean_text`、`_parse_int`、`_parse_date`、`_dedupe_names`、`_normalize_time_window` 等类似工具函数，存在轻微重复。

为什么现在还不算最糟：

- 后端没有引入多层抽象。
- 路由路径和数据流仍然直观。
- 大部分复杂度来自当前真实功能：参与者、权限、首尾截断、关键成员、总结。

真正难看的点：

- `_normalize_session_data()`、`_validate_create_payload()`、`_normalize_participants()` 都在一个文件中互相牵引。
- `_build_local_summary()` 和 `_build_ai_prompt()` 将统计、文案和 AI prompt 强耦合在 server.py。
- 共同工具函数在 `server.py` 和 `create_draft.py` 间重复。

建议处理顺序：

- 不要做 service/repository/controller 大分层。
- 可以轻拆：
  - `backend/session_normalize.py`：时间、姓名、参与者、session 归一化。
  - `backend/summary.py`：slot stats、本地总结、AI prompt。
  - `backend/common.py`：少量 `_clean_text`、`_parse_int`、`_parse_date`。
- `server.py` 保留路由和权限判断。

收益：

- 后端不会变平台化，但每个文件职责更清楚。
- 总结逻辑和创建/管理接口不会继续互相挤压。

### 5. `tests/test_api_smoke.py` 变成全功能回归脚本

位置：

- `tests/test_api_smoke.py:17`
- `tests/test_api_smoke.py:177`
- `tests/test_api_smoke.py:343`
- `tests/test_api_smoke.py:384`
- `tests/test_api_smoke.py:461`

现状：

- 一个文件包含 16 个测试，覆盖创建、加入、填写、读取、管理、删除、截断、关键成员、AI 草稿、存储级联。
- 测试名清楚，但领域越来越多。

为什么丑：

- 它已经不只是 smoke test，而是主要回归测试集。
- 失败时要在一个长文件里定位具体领域。
- 后续继续新增功能时，很可能继续往这个文件追加。

建议处理：

- 保留 `test_api_smoke.py` 做 3 到 5 条主链路冒烟。
- 拆出：
  - `test_session_lifecycle.py`
  - `test_session_management.py`
  - `test_summary.py`
  - `test_create_draft.py`
  - `test_storage.py`

收益：

- 测试结构和产品模块更一致。
- 每次改动能更快定位相关测试。

### 6. CSS 文件存在重复和历史堆叠迹象

位置：

- `frontend/styles.css:450`
- `frontend/styles.css:528`
- `frontend/styles.css:2184`

现状：

- `history-entry` 相关样式至少在多个位置出现。
- 文件超过 2000 行，已经很难快速判断某个组件样式的最终来源。
- 大量页面、弹层、表格、按钮、历史、AI、管理等样式都在一个文件里。

为什么丑：

- CSS 变成“只追加不整理”的状态。
- 同一组件样式散落时，后面的覆盖关系很难靠肉眼判断。
- 后续 UI 调整容易靠继续追加选择器解决，进一步恶化。

建议处理：

- 不引入 CSS 框架。
- 先按区域加清晰分段并消除重复：home / setup / join / main grid / overlays / history / responsive。
- 如果继续增长，再考虑拆为多个 CSS 文件，但不是第一步。

## 优先级建议

### P0：拆薄 `frontend/static/js/app.js`

这是当前最值得落实的代码清理。

建议第一刀只拆管理弹窗和 session actions，不碰业务行为：

- `manage.js`
- `session-actions.js`

### P1：整理 `render.js` 的表格渲染小函数

不要重做 UI，只抽重复模板，降低两套表格布局的维护成本。

### P2：清理 `index.html` 内联样式和内联事件

先清创建页和管理弹窗，因为它们和 `app.js` 大文件强耦合最明显。

### P3：后端轻拆 summary 与 normalize

后端可以晚一点动，因为当前测试能覆盖主链路，且过度拆层反而可能违背仓库原则。

### P4：测试按领域拆文件

这不改变产品，但会让后续维护更稳定。

### P5：CSS 去重和分段

先去重和分段，不急着拆文件。

## 不建议做的事

- 不要引入前端框架来解决当前问题。
- 不要把后端拆成 controller/service/repository 多层目录。
- 不要一次性重写表格渲染。
- 不要为了“干净”把所有 inline handler 一次性迁移，容易制造回归。
- 不要把 smoke test 全删，应该拆分而不是弱化测试。

## 最终结论

当前最乱的不是后端，也不是 AI，而是前端代码组织：`app.js` 太像万能控制台，`render.js` 太像模板字符串仓库，`index.html` 仍保留早期内联事件和样式习惯。

下一轮如果要继续落实“代码不过度”，建议从前端减法开始：

1. 拆薄 `app.js`。
2. 抽小 `render.js` 模板函数。
3. 清理 `index.html` 内联行为和样式。

一句话判断：

> 当前主要问题不是功能太多，而是太多功能还挤在少数几个文件里，用字符串、内联事件和全局函数勉强组织起来。
