# SQLite 存储重构方案

日期：2026-04-13

适用范围：记录本仓库从单表 `sessions(id, data, ts)` JSON 存储迁移到当前多表 SQLite 存储的设计依据与实施边界。

---

## 1. 目标

把当前“单表 + JSON Blob”的 SQLite 存储，重构为“少量清晰业务表 + 现有 API 基本保持不变”的结构。

重构目标不是平台化升级，而是解决当前已经出现的几个具体问题：

- 数据库层难以人工查看，不符合“偶尔像表格一样看和改”的使用习惯
- 单条参与者、单个时段、单项备注无法自然查询和修改
- 后续若要做后台查看、导出、排查数据问题，当前结构成本偏高
- 测试与调试现在强依赖 Python 内部数据结构，而不是数据库本身的可读性

明确不做：

- 不迁移到 PostgreSQL
- 不引入 ORM、Repository、Service 多层体系
- 不在本次重构中改产品交互或重做前端
- 不为了未来假想需求预埋复杂抽象

---

## 2. 原实现问题

重构前数据库初始化集中在 `backend/server.py`，表结构只有单表 JSON：

原表结构：

```sql
CREATE TABLE IF NOT EXISTS sessions (
    id   TEXT PRIMARY KEY,
    data TEXT NOT NULL,
    ts   INTEGER NOT NULL
)
```

其中 `data` 存的是整份会话 JSON，包含：

- 会话基础信息
- 创建者信息
- 预设参与者名单
- 关键成员名单
- 所有参与者
- 所有可用性数据

这个方案的优点是实现快，但缺点已经开始影响维护：

- 数据库工具里无法像普通表一样读数据
- 任何局部修改都要先读整段 JSON，再整体回写
- 删除一个参与者、修一条 availability，本质都是“读整条会话再整体覆盖”
- 数据层缺乏自然约束，很多校验只能依赖 Python 代码兜底

---

## 3. 重构原则

本方案必须遵守仓库根目录 [AGENTS.md](/d:/temp/meetup/AGENTS.md) 的约束：

- 先做最小可用，不做完整平台升级
- 优先增加薄存储层，不新建多层后端架构
- API 行为尽量不变，优先兼容现有前端与测试
- AI 功能边界不动，仍然只是草稿与总结，不下沉为数据库自动流程
- 如果一个需求能通过“少量新表 + 清晰函数”解决，就不要引入 ORM 和复杂迁移框架

因此，这次重构建议采用：

- 继续使用 `sqlite3`
- 继续把主要逻辑放在 `backend/server.py` 附近，但把数据库读写函数物理拆到独立模块
- 保持前端请求路径和响应结构尽量不变

---

## 4. 建议的新表结构

### 4.1 sessions

保存会话基础信息。

```sql
CREATE TABLE sessions (
    id TEXT PRIMARY KEY,
    schema_version INTEGER NOT NULL,
    name TEXT NOT NULL,
    date_s TEXT NOT NULL,
    date_e TEXT NOT NULL,
    hour_s INTEGER NOT NULL,
    hour_e INTEGER NOT NULL,
    first_hour_s INTEGER NOT NULL,
    last_hour_e INTEGER NOT NULL,
    creator_name TEXT NOT NULL,
    creator_token_hash TEXT NOT NULL,
    creator_prompt TEXT NOT NULL DEFAULT '',
    created_ts INTEGER NOT NULL,
    updated_ts INTEGER NOT NULL
)
```

### 4.2 session_expected_names

保存“预设参与者名单”。这部分独立出来后，不再和已加入参与者混在一列 JSON 中。

```sql
CREATE TABLE session_expected_names (
    session_id TEXT NOT NULL,
    name TEXT NOT NULL,
    position INTEGER NOT NULL,
    PRIMARY KEY (session_id, name),
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
)
```

### 4.3 participants

保存真实已加入的参与者。

```sql
CREATE TABLE participants (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,
    name TEXT NOT NULL,
    color TEXT NOT NULL,
    remark TEXT NOT NULL DEFAULT '',
    is_required INTEGER NOT NULL DEFAULT 0,
    token_hash TEXT NOT NULL DEFAULT '',
    created_ts INTEGER NOT NULL,
    updated_ts INTEGER NOT NULL,
    UNIQUE (session_id, name),
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
)
```

### 4.4 availability

保存参与者逐时段可用性。

```sql
CREATE TABLE availability (
    session_id TEXT NOT NULL,
    participant_id TEXT NOT NULL,
    slot_date TEXT NOT NULL,
    slot_hour INTEGER NOT NULL,
    state INTEGER NOT NULL,
    PRIMARY KEY (participant_id, slot_date, slot_hour),
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE,
    FOREIGN KEY (participant_id) REFERENCES participants(id) ON DELETE CASCADE
)
```

### 4.5 为什么不单独保留 `required_names` 表

当前代码同时存在：

- `requiredNames`
- `participants[].isRequired`

这是现有业务里已经存在的双源风险点。既然你不需要保留旧数据，这次建议顺手收敛成一套主表达：

- 对未加入的人：只在 `session_expected_names` 中存在名字
- 对已加入的人：以 `participants.is_required` 为准
- 对 API 返回：仍继续返回 `requiredNames`，但由存储层实时推导，而不是单独落一张表

推导规则：

- 已加入且 `is_required=1` 的名字，算关键成员
- 还没加入但在业务层被标记为关键成员的名字，需要单独保存

如果不想丢掉“未加入但已被标记关键成员”的能力，最小补充做法是增加一张非常薄的表：

```sql
CREATE TABLE session_required_names (
    session_id TEXT NOT NULL,
    name TEXT NOT NULL,
    position INTEGER NOT NULL,
    PRIMARY KEY (session_id, name),
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
)
```

最终建议：

- 保守方案：保留 `session_required_names`，实现最直接，和当前产品逻辑最一致
- 激进方案：把关键成员状态尽量折叠进 `participants`，但要重写更多同步逻辑

基于“最小可用”原则，**建议保留 `session_required_names` 表**。这样虽然仍然是两类数据，但边界更清楚，比现在的 JSON 双源更可控。

## 5. 推荐的最终最小表集

综合当前需求，推荐最终采用 5 张表：

- `sessions`
- `session_expected_names`
- `session_required_names`
- `participants`
- `availability`

这是当前业务能保持清晰的最小拆分，再继续压缩会重新变回难维护的混合结构，再继续扩张则开始过度设计。

## 6. 代码层实施方式

### 6.1 已新增文件

已新增：

- `backend/storage.py`

只负责：

- 初始化新 schema
- 按现有 API 所需格式读取会话
- 保存会话基础信息
- 保存参与者
- 保存 availability
- 删除会话 / 删除参与者

不负责：

- Flask 路由
- AI 起草逻辑
- 总结逻辑
- 输入校验规则

### 6.2 server.py 中的调整边界

`backend/server.py` 保留：

- 路由
- 参数校验
- token 判断
- summary 计算
- create_draft 集成

下面几类函数已迁出或改薄：

- `init_db`
- `get_db`
- `_load`
- `_save`
- `_delete`

目标状态是：

- `server.py` 继续处理“请求 -> 校验 -> 业务组装 -> 返回”
- `storage.py` 负责“数据库结构 -> SQL -> Python 数据组装”

这符合当前仓库风格，也不会引入额外抽象层。

## 7. 对现有 API 的影响评估

### 7.1 可以保持不变的部分

下面这些前端接口理论上都可以保持路径和响应结构不变：

- `POST /api/session`
- `GET /api/session/<sid>`
- `POST /api/session/<sid>/join`
- `PUT /api/session/<sid>/avail`
- `PATCH /api/session/<sid>`
- `DELETE /api/session/<sid>`
- `DELETE /api/session/<sid>/participants/<pid>`
- `GET /api/session/<sid>/summary`

### 7.2 需要重点注意的兼容点

- `GET /api/session/<sid>` 仍需返回当前前端依赖的聚合结构，尤其是 `participants[].avail`
- `PATCH /api/session/<sid>` 当前支持一次性回传整份 `participants`，存储层要正确转成多表写入
- `requiredNames` 和 `participants[].isRequired` 的同步逻辑必须保持现有行为
- `summary` 逻辑大量依赖内存中的聚合 session 结构，所以存储层必须继续提供与现在接近的 `_load` 输出

结论：

- **API 层可以基本不动**
- **存储层必须提供聚合读模型**

这意味着本次重构的关键不是前端改动，而是后端如何从多表重新拼回现有 session dict。

## 8. 测试影响评估

当前测试文件是 [tests/test_api_smoke.py](/d:/temp/meetup/tests/test_api_smoke.py)。

它的特点是：

- 大部分测试只关心 API 行为，不关心底层存储结构
- 少部分测试直接调用了 `server._save()` / `server._load()`
- `setUp()` 现在直接执行 `DELETE FROM sessions`

因此实现上完全可行，但要做以下调整：

### 必改

- 测试清库逻辑要改成按新表顺序清空
- 直接依赖 `_save()` / `_load()` 的测试要改成调用新的 storage 包装函数，或保留兼容函数名

### 建议新增

- 新增 1 个存储层测试，验证 `_load` 能正确把多表拼装成旧结构
- 新增 1 个删除级联测试，验证删会话会清掉 `participants` 与 `availability`

结论：

- **测试成本中等，可控**
- 风险主要在“多表读回聚合结构时漏字段”

## 9. 可实现性评估

结论：**可以实现，而且现在是合适窗口。**

原因如下：

- 现有数据量很小，你明确允许不保留旧数据，避开了迁移历史数据的复杂度
- 现有 API 边界已经相对稳定，适合做“内部存储替换”
- 当前项目仍然是 Flask + `sqlite3` 的简单后端，改造成本仍在可控范围
- 前端主要依赖聚合后的 JSON，会增加一些后端拼装工作，但不需要同步重做界面

最大的真实成本不是 SQL 本身，而是以下三件事：

1. 把 `requiredNames` / `isRequired` 关系重新收口
2. 让 `PATCH` 的整表修改继续稳定工作
3. 让 `_load` 拼出的结构继续满足 summary 和测试

综合判断：

- 技术上可实现
- 风险可控
- 值得做

## 10. 不建议现在做的内容

以下内容和本次目标不匹配，建议明确排除：

- 引入 SQLAlchemy / Alembic
- 把后端拆成 controller/service/repository 多层目录
- 顺手改 REST 资源设计
- 顺手给前端做后台数据管理器
- 迁移到 PostgreSQL
- 同时做“数据库重构 + AI 逻辑拆分 + 前端大改版”

这些会明显超过本仓库当前的复杂度预算。

## 11. 建议的实施顺序

### 阶段 1：落新 schema，不动接口

- 新增 `backend/storage.py`
- 定义新表结构和初始化逻辑
- 保留 `server.py` 现有 API 路由
- 先实现新的 `load/save/delete` 聚合函数

### 阶段 2：切换接口到新存储层

- 把 `create / read / join / avail / patch / delete` 全部切到新存储函数
- 保持响应 JSON 不变
- 跑现有 smoke tests

### 阶段 3：清理旧 JSON 存储遗留

- 删除旧的单表 `sessions(data, ts)` 初始化逻辑
- 删除只服务于旧 JSON 落库的兼容代码
- 补充最少量存储层测试

因为你不需要保留旧数据，所以不建议单独再做迁移器，直接清空本地库并按新 schema 初始化即可。
